# GDPR engine (myelin-gdpr-service, myelin-gdpr, myelin-gdpr-macros)

_The GDPR engine is unusually well-built: total/ordered DSR state machine, deny-by-default residency gate, fail-safe-to-suspend legal holds, canonical Identity-first erase order, PII-free content-addressed receipts, and heavy mutation-tested coverage throughout. The macro/registry (classify-derive, DPIA router, consent/sub-processor/transfer registries, retention tightest-wins merge) are correct and thoroughly tested. The one substantive defect is in the erasure-ledger write path: the ledger records the DSR SUBMISSION time as the post-restore re-erasure offset instead of the completion time, which can silently resurrect an erased subject on a backup restore whenever the submit→complete window (notably a legal-hold defer/resume) straddles the backup point-in-time. A secondary low-severity gap: the derive's compile-time untagged-PII check only matches exact field names, missing common variants like `user_email`._

**Kept findings:** 2  (🟠 1 high  ·  🔵 1 low)

---

### 1. 🟠 Erasure ledger records the DSR SUBMISSION time as the post-restore re-erasure offset, so a restore can resurrect an erased subject

- **Severity:** high  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** durability
- **Location:** `crates/myelin-gdpr-service/src/fanout.rs:447`

**What:** In `FanOutDriver::drive` the timestamp base is captured as `let now = req.submitted_at_secs;` (fanout.rs:447). On a completed erase this same `now` is passed to `write_erasure_ledger_entry(id, &req.scope, &holder_receipts, now)` (fanout.rs:527), which forwards it to `ErasureLedger::record_completion` as BOTH `completed_at_offset` and `completed_at_secs` (fanout.rs:571-579). `submitted_at_secs` is set once at DSR creation (`submitted_at_secs: now` where `now = self.clock.now_secs()`, dsr.rs:529/542) and is never mutated thereafter, so it is strictly the submission time, not the completion time. `post_pit_records_after(pit)` (erasure_ledger.rs:282-293) returns exactly the entries with `completed_at_offset > pit` — the subjects a restore of PIT `pit` must re-erase. Recording the submission offset means an erasure submitted before a backup PIT but crypto-shredded after it is stamped `completed_at_offset <= pit` and is NOT selected for re-erasure. The value also contradicts its own doc comment (fanout.rs:539-545 / :577), which asserts it is the completion timestamp, monotone and strictly ordered with restore PITs.

**Impact:** Silent post-restore resurrection of an erased subject (Art. 17 / GD-14 failure the module calls 'the gravest data-handling failure'). The submit-to-complete gap is real: the legal-hold path (fanout.rs:456-469 `HoldVerdict::Deferred`) returns early WITHOUT running the fan-out, leaving the DSR parked at AwaitingHolders; on hold-lift `drive` is re-called days/weeks later and re-reads the still-pinned `req.submitted_at_secs`. Scenario: DSR submitted at T0 under a legal hold; backup taken at T1>T0 (subject still live, DEK present); hold lifted and subject crypto-shredded at T2>T1; ledger records completed_at_offset=T0. A restore to T1 revives the subject's DEK, and `post_pit_records_after(T1)` skips the entry (T0<T1) — the subject is resurrected and never re-erased. The bug also fires for any ordinary erase whose processing latency straddles a backup PIT (T0<T1<T2), not only the hold path.

**Fix:** Timestamp the ledger entry at COMPLETION, not submission: capture a fresh completion offset (the driver/orchestrator clock `now_secs()` read at the point the DSR reaches `Completed`, or the real WAL cursor once wired) and pass THAT into `write_erasure_ledger_entry`/`record_completion`. Keep the deterministic submission-based `now` only for the content-addressed receipt (which needs re-drive idempotency). Add a drill where submit < pit < complete (ideally via the defer/resume path) and assert the subject IS returned by `post_pit_records_after(pit)`.

> _Verifier note:_ Verified fanout.rs:447 (`now = req.submitted_at_secs`), the deferred early-return at 456-469, the completed-erase ledger write at 526-527, write_erasure_ledger_entry at 546-580 passing `completed_at_secs` into both record_completion offset args (577-578), erasure_ledger.rs post_pit_records_after filter `completed_at_offset > pit` (286), and dsr.rs:529/542 confirming submitted_at_secs is the creation-time clock value and is never updated. The doc's own 'monotone + strictly ordered' invariant is what the code violates for any non-instant completion. Confirmed high; the M1 WAL-offset floor documented at fanout.rs:539-545 does not excuse using submission time — even the surrogate should be a completion-time read.

### 2. 🔵 Compile-time untagged-PII rejection only fires on exact field-name matches, missing common PII name variants

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** correctness
- **Location:** `crates/myelin-gdpr-macros/src/lib.rs:208`

**What:** `is_pii_field` (lib.rs:208-210) is `PII_FIELDS.contains(&name)` — an exact whole-identifier match against a fixed list (lib.rs:89-107: `email`, `name`, `phone`, `address`, `body`, `full_name`, `message_body`, `comment_text`, ...). It is called from the derive guard at lib.rs:157-159 which emits the `no-untagged-personal-data` compile_error only on an exact hit. Compound/prefixed real-world PII names — `user_email`, `email_address`, `contact_phone`, `home_address`, `recipient_name`, `author_email`, `msg_body` — match no entry, so a struct deriving `PersonalData` with such an untagged field expands cleanly and the guard does not fire.

**Impact:** A schema author who names a PII column with a prefixed/compound identifier and forgets `#[personal_data(...)]` gets no compile error; the field silently escapes the generated registry and therefore the data map, RoPA, and the erasure/breach fan-out driven from the map — the exact un-erasable/un-mapped-subject bug class the guard exists to foreclose. This is a defense-in-depth gap, not a primary failure: the correct posture is authors tag PII fields, and this is one of two 'belt-and-braces' layers — hence low, not higher.

**Fix:** Match PII fingerprints as `_`-delimited segments or substrings of the lower-cased field identifier rather than exact whole-name equality, or at minimum document the exact-match set as a known gap. Since the doc comment (lib.rs:85-88) states the macro list and the `myelin-lints` source scanner are 'kept in sync by convention', factor the fingerprint set into one shared constant so the two lists cannot drift and so a matching-strategy fix applies to both.

> _Verifier note:_ Verified lib.rs:208-210 (exact `contains`), the guard call site lib.rs:157-166 emitting the compile_error, and PII_FIELDS contents at lib.rs:89-107 — none of the cited compound variants are present. Confirmed as described. Low severity is correct: it is a redundant compile-time guard layer, not the sole control; the primary defense remains explicit tagging plus the separate lints scanner (which the doc says shares the same convention and could share the same gap, but that crate is out of this unit's scope and unverified here).
