### 1. 🔵 Finalized agent message live-delivery frame carries message_id in the correlation_id field, breaking partial-stream reconciliation

- **Severity:** low  ·  **Verdict:** 🟨 PLAUSIBLE  ·  **Category:** correctness
- **Location:** `crates/myelin-chat-gateway/src/delivery.rs:148`

**What:** `LiveFrame::from_message` maps an `AuthorKind::Agent` message to `LiveFrame::AgentPartial { correlation_id: msg.message_id.0.clone() }` — it puts the durable message_id into a field named `correlation_id`. But the streamed `agent.message.partial` frames produced during the run (presence.rs `PartialFrame.correlation_id` / `StreamSession.correlation_id`) carry the RUN's correlation_id, not the message_id. The message_id is only known at `finalize` time and was never sent on the earlier partial frames. The two frame families therefore key on different identifiers.

**Impact:** A client that dedups the in-flight "working…" partial bubble (keyed by the run correlation_id) against the final delivery frame cannot match them via the `correlation_id` field, since the final frame's value is the message_id. The final agent message would render as a new bubble beside the streamed partial rather than replacing it. The durable record is still correct (resume recovers it), so this is a live-UX/reconciliation defect, not data loss.

**Fix:** Either carry the run correlation_id (not message_id) on the finalized agent delivery frame, or add a distinct `message_id` field so the client can reconcile the final against the partial stream by the same key the arch §7.3 reconciliation names. Confirm against the actual client reconciliation protocol whether partials are ever re-tagged with the message_id at finalize.

> _Verifier note:_ Confirmed at lines 148-150: LiveFrame::from_message maps AuthorKind::Agent to AgentPartial{correlation_id: msg.message_id.0.clone()}, putting the durable message_id into a field whose own doc (lines 58-59) says it is 'The run correlation id the final durable message reconciles the partial against.' presence.rs confirms the partial stream (PartialFrame.correlation_id, StreamSession::open) keys on the RUN correlation_id while message_id is only supplied separately at finalize()/ResumeView::Final. So the field genuinely holds a different identifier than the like-named field on the partial stream — a real internal contradiction. But (a) from_message/deliver_message have NO wired production caller (grep found only unrelated LiveSurface::AgentPartial shed-surface refs), and (b) actual reconciliation here is server-side via StreamSessions keyed by correlation_id, so the client-side mis-render impact depends on an unwired client protocol not visible in source. Real code fact; inferred impact -> PLAUSIBLE, severity low correct.

### 2. 🔵 MemHotTier::append writes the message row eagerly outside the outbox transaction, contradicting the module's unconditional emit-iff-committed claim

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** data-integrity
- **Location:** `crates/myelin-chat/src/store/mod.rs:534`

**What:** In `MessageStore::append`, the message row is inserted into `self.partitions` at line 534, then the lock is dropped and the fallible co-commit runs (`tx.stage_state_change` + `emit_message_event(...)?`). The actual message data is written directly to the store, never through `tx`; only a state-change string is staged. If `emit_message_event` returns Err (e.g. `mint_message` or `tx.emit` failure) or the caller later aborts the transaction, the inserted message row persists with no corresponding `chat.message.created` event. The module doc (lines 52-57 / 273-276) states unconditionally that "an aborted transaction writes NEITHER the message NOR its event". `membership.rs` explicitly documents and works around this exact in-memory-floor ordering hazard (write the fallible part first), but `append` does the opposite: it commits the store mutation before the fallible emit.

**Impact:** In the in-memory (DB-free) tier the store and the outbox can diverge: an emit failure or aborted co-commit leaves an orphaned message (row present, event absent), violating the stated co-commit atomicity. Scope is the in-memory floor; the real PG binding (pg.rs, behind `integration`) is expected to co-commit in one DB transaction. Low severity because emit failures are rare and the tier is the dev/test floor, but the doc overstates the guarantee.

**Fix:** Either reorder so the fallible emit is staged before the irreversible store insert (mirroring membership.rs), or scope the doc claim to the PG tier and note the in-memory floor's eager-write caveat. At minimum, on `emit_message_event` error, roll back the just-inserted row before returning Err.

> _Verifier note:_ Confirmed: line 534 `log.insert(message_id.clone(), stored)` is a direct in-memory BTreeMap mutation NOT bound to tx; line 541 drops the lock; lines 542-550 then run the fallible co-commit (tx.stage_state_change + emit_message_event(...)?). emit_message_event (lines 292-331) has two Err paths — mint_message (line 304) and tx.emit (lines 328-329), both mapped to StoreError::Cold. On either error, or a later caller-side tx abort, the row inserted at 534 is NOT rolled back (no tx handle over self.partitions), producing an orphaned message with no chat.message.created event. This contradicts the module doc's unconditional claim (lines 52-57 / 275-276) that an aborted transaction writes NEITHER the message NOR its event. membership.rs (lines 52-57) documents this exact in-memory-floor ordering hazard and deliberately writes the fallible part FIRST; append does the opposite. Correctly scoped to the in-memory floor (PG binding co-commits in one DB tx). CONFIRMED, low.
