# Control plane & query (myelin-control-plane, myelin-query)

_I deep-read the control-plane orchestration and query cores rather than skimming. In myelin-query: the bounded predicate engine (lib.rs: QueryAst::validate/eval, Predicate::node_count/depth/eval, CmpOp::apply, literals_eq — MAX_PREDICATE_NODES/DEPTH/MAX_EVAL_STEPS all enforced and fail-closed), the parse.rs recursive-descent lexer/parser (lex, lex_string, Parser::parse_or/and/not/primary with MAX_PARSE_DEPTH), matcher.rs (EventMatcher::matches, setexpr_contains, project_envelope, subject_object_id, subject_filter_of), view.rs (ViewSpec), order_key.rs (tiebreak, CONFORMANCE_VECTOR), signals.rs (SignalEngine::ingest, DedupKeyTpl::render, parse_rfc3339_secs), automations.rs (AutomationEngine::fire_one, DurableExecutor/InMemoryExecutor), dispatch.rs (DispatchTier::decide/dispatch, DispatchBreaker, InMemoryCostGate). In myelin-control-plane: registry.rs (Registry::check_placement_invariant/place_tenant — the HARD region pin), place.rs (PlacementService::place, assign_cell region-first→tier→capacity→stability), provision.rs (ProvisioningGate::provision_cell restore-verify+readiness gating, decommission_tenant), migration.rs (LiveMigration::migrate_tenant atomic cut-over + crypto-shred), isolation.rs (tier-invariant PartitionKey), cross_cell_bridge.rs (CrossCellBridge::resolve/rollup — cell-local resolution, tombstone-on-deny). The code is largely healthy: the placement invariant, the permission-compose 0-leak ordering (visibility tested before predicate), fail-closed predicate evaluation, and effectively-once idempotency are all real and mutation-tested. The findings are a reserved-cost/telemetry leak on the dispatch delivery-failure path, a defense-in-depth tenant/type-scoping gap in EventMatcher::matches, and a per-event full-rules clone on the firehose consumers._

**Kept findings:** 3  (🟡 1 medium  ·  🔵 2 low)

### 1. 🟡 Dispatch delivery failure leaks the cost reservation and mislabels itself as a breaker shed

- **Severity:** medium  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** correctness
- **Location:** `crates/myelin-query/src/dispatch.rs:784`

**What:** In DispatchTier::decide, the gauntlet reserves cost (step 6, `self.cost_gate.reserve(...)` at line 765) and records the dispatch against the per-tenant breaker (`record_and_check` at 776-778) BEFORE calling `self.target.deliver(&action)`. When deliver returns Err, the arm at 791-796 returns `Disposition::BreakerShed { reason: BreakerOpen }` but never releases the reservation and never decrements in-flight. The CostGate contract states the reservation is settled by "the run" after it starts — but on a delivery failure the run never starts, so the reserved balance and the in-flight slot for that run_ref are consumed permanently (no settle path exists in this tier). Additionally, a genuine inbox/transport failure is reported as `BreakerShed(BreakerOpen)` with `tripwire_fired` still carried through, so DispatchTelemetry.breaker_shed (and possibly tripwire_firings) increments for an event that was neither breaker-tripped nor a shed — corrupting the BUS-D6 observability the tier is supposed to make trustworthy.

**Impact:** Repeated delivery failures (agent inbox unreachable) accumulate reserved-but-never-settled in-flight slots per distinct run_ref, eroding the per-tenant DISPATCH_INFLIGHT_CAP and debiting balance for runs that never executed; and the shed/breaker telemetry misattributes transport failures to the circuit breaker, hiding real inbox outages behind a breaker-shed count.

**Fix:** Add a distinct disposition (e.g. DeliveryFailed) for a target.deliver Err, and on that path release the reservation / decrement in-flight (or defer reserve until after a successful deliver). Do not carry tripwire_fired into the failure arm, and give it its own telemetry counter so an inbox outage is observable as such.

> _Verifier note:_ Confirmed in decide() (dispatch.rs:764-797). Step 6 reserve() (765) debits balance and inserts run_ref into the in_flight set; record_and_check (776-778) records the dispatch. On target.deliver Err (791-796) the arm returns Disposition::BreakerShed{ shed: lane_shed(BreakerOpen) } with tripwire_fired carried through. The CostGate trait (322-332) exposes ONLY reserve + in_flight — there is no settle/release method anywhere in the tier, and InMemoryCostGate.reserve (378-405) confirms reserve mutates balance and in_flight with no compensating release. So a delivery failure permanently holds the in_flight slot and debit for that run (bounded to distinct run_refs, since reserve is idempotent on run_ref per 380-388 — the finding correctly scopes this to 'distinct run_ref'). Telemetry mislabel confirmed: record() (532-548) increments breaker_shed on the BreakerShed arm (543) and increments tripwire_firings when the carried tripwire_fired is true (546-547), so a genuine transport failure is counted as a circuit-breaker shed. Medium is appropriate: real observability corruption + slot/balance leak, but requires delivery failures and impact is bounded; a durable ledger reconciler (outside this crate) may mitigate the leak in production, which is why the tier-local behavior is the confirmable part.

### 2. 🔵 EventMatcher::matches authorizes on the bare last-segment id, ignoring the ref's tenant and type

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** tenant-isolation
- **Location:** `crates/myelin-query/src/matcher.rs:167`

**What:** EventMatcher::matches (167-186) reduces the envelope subject to `subject_object_id(&envelope.subject)`, which (208-213) strips everything but the final `/`-segment of `myelin://<tenant>/<subsystem>/<type>/<id>`, then tests membership of that bare id in the caller-supplied `visible` SetExpr. The matcher's own `object_type` field is NOT consulted anywhere in the match path (confirmed: it is only exposed via the accessor at line 120 and named in a doc comment), and neither the tenant nor the type segment of the ref is compared against anything. The 0-leak property therefore rests entirely on (a) the caller computing `visible = list_objects(viewer, read, type)` for exactly the right tenant+type and (b) object ids being globally unique across the whole id space `visible` ranges over. If ids are only unique per (tenant,type) — as the test fixtures using ids like "42"/"PROJ-1" suggest is possible — an envelope for tenant B's artifact with an id that collides with an id in tenant A's visible set would pass the visibility gate and have its predicate evaluated, in a subsystem whose HARD principle is multi-tenant isolation.

**Impact:** No active leak in a correctly per-tenant-partitioned firehose, but there is zero defense-in-depth: a mis-scoped `visible` set, an id-space collision across tenants/types, or a consumer that ever sees a foreign-tenant envelope would be matched/curated/dispatched across the tenant or type boundary, and nothing in the matcher catches it.

**Fix:** In matches(), also verify the subject ref's tenant segment (and ideally its type segment against self.object_type) matches the scope the visible set was computed for, so the 0-leak property is structural in the matcher rather than delegated entirely to the caller and to global id-uniqueness.

> _Verifier note:_ Structural facts all confirmed. matches() (167-186) computes object_id = subject_object_id(&envelope.subject); subject_object_id (208-213) strips to the last '/'-segment (sans #anchor), discarding the tenant and type segments of myelin://<tenant>/<subsystem>/<type>/<id>. The match path uses only object_id (via setexpr_contains) and self.predicate.eval — self.object_type is never read in matches() (only exposed via the accessor at 118-121 and used by callers to compute list_objects(viewer, read, type)); envelope.tenant is never compared. The 0-leak property is therefore fully delegated to the caller-supplied `visible` set and to id-uniqueness, exactly as the doc comment (146-166) states by design. HOWEVER the finding's own impact concedes 'No active leak in a correctly per-tenant-partitioned firehose' — this is a defense-in-depth observation, not a demonstrable isolation break, and it hinges on runtime id-uniqueness / caller wiring not verifiable from source. Downgraded from medium to low: the code behaves as documented; there is no reproduced cross-tenant leak. (Note: SignalEngine keys its store by (envelope.tenant, key) at signals.rs:381/408, so the engine layer does carry tenant even though the matcher does not.)

### 3. 🔵 Firehose consumers clone the entire rule set (QueryAst trees) on every event

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** efficiency
- **Location:** `crates/myelin-query/src/signals.rs:373`

**What:** SignalEngine::ingest does `let rules = self.rules.clone();` (373) on every ingested event to sidestep the borrow conflict between iterating rules and mutating self.store; AutomationEngine::ingest does the same at automations.rs:477. Each rule embeds one or two EventMatcher/QueryAst predicate trees plus dedup templates, so this is an O(rules) deep clone per event on precisely the components the module docs call "the raw evt.* firehose" (SignalEngine is one of the few full-firehose consumers). The comment acknowledges it as "the per-event cost."

**Impact:** Per-event allocation and deep-copy of every predicate tree scales the firehose hot path with rule count; under a high event rate with many rules this is avoidable steady-state churn.

**Fix:** Restructure so the rule list is iterated by reference while store/budget mutations are staged (e.g. collect the store keys/mutations first, or split rules and store into separately-borrowable fields / take rules out with std::mem::take and put back), avoiding the per-event full clone.

> _Verifier note:_ Confirmed. SignalEngine::ingest does `let rules = self.rules.clone();` at signals.rs:373 on every event, with the comment (370-372) explicitly calling it 'the per-event cost'. AutomationEngine::ingest does the same at automations.rs:478 (`let rules = self.rules.clone();`). SignalRule (203-218) embeds matcher: EventMatcher plus resolves: Option<EventMatcher> plus dedup_key_tpl, and EventMatcher wraps a QueryAst predicate tree, so the Vec clone is an O(rules) deep clone of every predicate tree per ingested event on the full-firehose hot path. Efficiency/low is accurate; the clone is a deliberate borrow-conflict workaround (iterate rules while mutating self.store), avoidable via mem::take-and-restore or field splitting as the finding recommends.
