# Cross-cutting: tenant isolation & authorization propagation

_I traced multi-tenant isolation and authz propagation from the edge inward and the cross-tenant story is genuinely robust — this is not a placeholder pass. Concretely I read: myelin-edge (gateway.rs Gateway::handle_inner/authenticate/resolve_scope, request.rs EdgeRequest, session.rs SessionStore httpOnly-cookie machinery, error.rs EdgeError oracle-free 401/403 envelope, authz.rs, sse.rs SseHub, git_edge.rs handlers + register_git, git_durable.rs); myelin-storage/src/rls.rs (TenantScope::from_verified_token / resolve — the sole scope constructor, no from_path); myelin-substrate/src/topology.rs (PublicSurface::resolve_tenant IDOR reject+audit, InternalSurface::handle re-authorize, Authorizer trait); myelin-identity-service authenticate.rs + machine_auth.rs (CapabilityAuthenticator::authenticate — tenant-from-verified-token, partitioned revocation consult, authority-ceiling, no cross-tenant credential lookup) and lib.rs StoreBackedCheck::check/list_objects (fail-closed Deny); myelin-search/src/pipeline.rs (query_consistent_with_vector — ScopedEngine tenant re-check QueryError::TenantMismatch, exactly-one list_objects ACL conjoin, AclFilter::None short-circuit, never widened to All); myelin-events/src/firehose.rs (bounded-selector, never `*`); myelin-git/src/gix_backend.rs (validate_path_segment / validate_repo_slug path-traversal fail-closed); myelin-notif/src/list_inbox.rs (recipient-scope + tenant-scope + step-0 check-read authorize). The tenant-from-token discipline is enforced structurally at every layer I inspected: the URL path is never the source of the operating tenant, the only TenantScope constructor requires a verified Principal, path/token mismatches are rejected and audited, and git repo paths are traversal-hardened. The two findings below are intra-tenant, object-level gaps (not cross-tenant leaks): the edge Authorizer seam is action-scoped only and no Zanzibar object `check` is invoked at the gateway or in the git handlers._

**Kept findings:** 2  (🟡 1 medium  ·  🔵 1 low)

---

### 1. 🟡 Edge re-authorization is action-scoped only — no object-level Zanzibar check at the gateway, so intra-tenant object isolation is unenforced for object-addressed routes

- **Severity:** medium  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** authorization
- **Location:** `crates/myelin-substrate/src/topology.rs:269`

**What:** The Authorizer seam the gateway re-authorizes every call through is `fn authorize(&self, principal: &Principal, action: &str) -> bool` (topology.rs:269) — it receives only a static action string, never the target object id. In gateway.rs:235 the dispatch calls `self.authorizer.authorize(&principal, &route.action)` where `route.action` is a fixed label like "git.pr.view". Object-addressed routes such as `GET /v1/git/repos/{repo}/prs/{n}` and `/v1/git/repos/{repo}/blob/{ref}/{path}` therefore pass the SAME coarse check regardless of which repo/PR/blob is named. The git read handlers (RepoListHandler, PrOverviewHandler, PrChecksHandler, BlobViewHandler, CodeSearchHandler in git_edge.rs, and the durable handlers in git_durable.rs) then key their lookups on `ctx.scope.tenant()` ONLY and never call `check`/`list_objects` (confirmed: the only `Id.check` occurrences in those files are comments). Compounding this, HandlerCtx (catalogue.rs:139) exposes `principal`, `scope`, `params` but carries NO check/authorize port, so an edge handler cannot perform an object-level decision even if it wanted to. Contrast myelin-notif::list_inbox, which correctly runs a per-item `authorize.can_read(principal, subject, at) == Decision::Allow` step-0 filter. The real object-level engine exists (StoreBackedCheck::check in identity-service/lib.rs:1357) but is simply not wired into the edge path.

**Impact:** Cross-tenant isolation is intact (tenant-from-token holds everywhere). But WITHIN a tenant there is no object-level authorization at the edge: any authenticated principal who passes the coarse RBAC-style action check can read every repo, PR, blob and code-search hit belonging to their tenant, regardless of per-repo/per-PR permissions. Because git_edge is the explicitly-declared template every subsequent subsystem (issues/chat/knowledge/CI) follows, the action-only seam risks propagating the same intra-tenant over-share into those subsystems. (git_edge's backing store is currently in-memory demo data, which bounds present-day exposure, but the seam shape is the durable contract.)

**Fix:** Extend the edge authorization to be object-aware for object-addressed routes: either widen the Authorizer seam to accept the resolved object ref (so it can lower to the identity `check(subject, permission, object, at)` engine that already exists), or thread a BoundedCheckPort into HandlerCtx and require object-addressed read/write handlers to run a per-object `check` (as notif::list_inbox does) before serving. At minimum, add a lint/contract test asserting that any route carrying an object path-param (`{repo}`, `{n}`, `{path}`) invokes an object-level check rather than relying on the action label alone.

> _Verifier note:_ Verified all cited lines. topology.rs:269 `authorize(&self, principal, action: &str) -> bool` takes only an action string — verbatim match. gateway.rs:235 calls it with `&route.action` for every route before dispatch. git_edge handlers (PrOverviewHandler/PrChecksHandler/BlobViewHandler/CodeSearchHandler) key lookups on (tenant, repo, n/path) and never invoke check/list_objects. git_durable object-addressed routes (DPrOverview→git.pr.view, DBlobView→git.blob.view at git_durable.rs:1109-1116) are gated by action label only; the `Id.check(repo_admin)` references at lines 439/1134 are comments, and crucially the seam signature cannot carry the resolved {repo}/{n}/{path} object, so even a production authorizer cannot make an object-level decision. catalogue.rs:139 HandlerCtx exposes principal/scope/params/page/request with no check port — confirmed. The notif contrast is real: list_inbox.rs applies a per-item `authorize.can_read(principal, &row.subject, at) == Decision::Allow` step-0 filter. The real engine StoreBackedCheck::check(subject, permission, object, at, caveat) exists at identity-service/lib.rs:1357 (finding omitted the extra caveat param — immaterial) but is not wired to the edge. Cross-tenant isolation holds (tenant-from-token); intra-tenant object-level authz is genuinely absent. Severity medium is right: real confidentiality gap on the durable backend and the declared template for all subsystems, but cross-tenant safe and git_edge backing is demo data (main.rs also injects an AllowAll authorizer, so today every action passes anyway).

### 2. 🔵 SSE subscription scope is tenant-coarse with only an action-level gate — latent intra-tenant cross-resource event leak once a subsystem wires per-resource SSE

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** tenant-isolation
- **Location:** `crates/myelin-edge/src/gateway.rs:256`

**What:** For an SSE route the gateway subscribes with `self.sse.subscribe(stream, &sse_scope_for_tenant(&scope.tenant().0))` (gateway.rs:256), i.e. the subscription scope is `tenant:<t>` — the verified tenant and nothing finer. The only authorization applied is the same action-level `authorizer.authorize(principal, route.action)` gate. sse.rs's SseHub keys broadcasts on `(stream, scope)`, so every subscriber on `(stream, tenant:<t>)` receives every frame any publisher sends to that key. sse.rs's own doc-comment envisions the scope as "verified tenant + an optional bounded resource id", but the gateway never passes a resource id — it always collapses to tenant granularity. There is also no per-frame `check` filter (unlike notif::list_inbox). No subsystem currently registers an sse_route (git_edge registers none), so this is latent, not live.

**Impact:** When a subsystem wires a per-resource SSE route (e.g. `/v1/chat/channels/{channel}/stream` gated by `chat.channel.watch`) using this convention, a principal who passes the coarse action check subscribes to the whole `(chat, tenant:<t>)` stream and receives frames for EVERY channel in the tenant, not just the channel they addressed — an intra-tenant cross-resource event leak. Cross-tenant remains safe (the scope is always the verified tenant).

**Fix:** Have sse_route derive the bounded scope from the verified tenant PLUS the route's resource path-param (e.g. `tenant:<t>|channel:<id>`), mirroring the firehose BoundedSelector grammar, and gate the subscription with an object-level `check` on that resource (not just the action label) at subscribe time. Encode the tenant+resource scope contract as a test so a subsystem cannot register a tenant-coarse SSE route for an object-addressed stream.

> _Verifier note:_ gateway.rs:256 subscribes with sse_scope_for_tenant(scope.tenant().0), which returns `tenant:<t>` (gateway.rs:43) — tenant-granular, no resource id. The same action-level authorizer.authorize gate (line 235) is the only authz; no per-frame check. SseHub keys broadcasts on (stream, scope) (sse.rs), and sse.rs's own doc (lines 12-13, 95-96) envisions 'verified tenant + an optional bounded resource id' that the gateway never supplies. One factual correction to the finding: it claims 'No subsystem currently registers an sse_route' — main.rs:60 DOES register `.sse_route("/v1/t/{tenant}/events", "edge.events.subscribe", "edge")`. But that route is legitimately tenant-level (sole path param is {tenant}, consumed by the IDOR guard; no finer resource to leak across), so it is correctly scoped and not itself a leak. The finding's substantive claim — that an object-addressed per-resource SSE route (e.g. /chat/channels/{channel}/stream) would collapse to tenant scope and fan every channel's frames to any tenant subscriber — remains accurate and latent since no such per-resource route exists yet. Cross-tenant remains safe. Low severity confirmed.
