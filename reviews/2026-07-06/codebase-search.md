# Search (myelin-search)

_myelin-search is an unusually mature, defensively-written, mutation-tested crate: the query compiler (cost-bounded, type-checked, no silent coercion), the mandatory-ACL engine seam, per-tenant scoping via the verified-principal tenant check (pipeline.rs:790), and the no-stale-grant/fail-static consistency path are all solid and free of obvious authz-bypass or injection holes on the lexical path. The one substantive defect is a divergence between the lexical and vector ACL enforcement: `AclFilter::admits` (the filter-during-traversal predicate the semantic/RAG path uses) checks only `doc_id`, while the posting-list `acl_clause` matches `doc_id OR acl_object` — so for sub-artifact documents (acl_object=parent) a deny-set answer leaks denied children through semantic search and an allow-set hides permitted children, contradicting the crate's own 'one ACL meaning, no drift' invariant. A second, lower-severity issue is that end-user full-text query text is parsed as Tantivy's query DSL, allowing field-scoped probing (ACL still applies), parse-error failures on ordinary text, and an unbounded literal that escapes the cost guard._

**Kept findings:** 2  (🟠 1 high  ·  🔵 1 low)

---

### 1. 🟠 Vector/RAG ACL filter (`AclFilter::admits`) matches only `doc_id`, ignoring `acl_object` — semantic search leaks denied sub-artifacts (and hides permitted ones)

- **Severity:** high  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** tenancy
- **Location:** `crates/myelin-search/src/engine.rs:238`

**What:** The lexical/structured path lowers an `AclFilter` via `acl_clause` (engine.rs:534-548), which matches a document when its `doc_id` OR its `acl_object` is in the set (the two-field term set over [schema.doc_id, schema.acl_object]). The vector/semantic path (`semantic()` at engine.rs:1025-1028) instead evaluates `AclFilter::admits(doc_id)`, which only ever compares against `doc_id` (Ids at engine.rs:238, NotIds at engine.rs:239, composed by And/Or/Not at 240-243). `VectorRecord` does not store `acl_object` (vector.rs:154-162), and `knn_filtered` calls `visible(&node.record.doc_id)` (vector.rs:516) so it physically cannot apply a parent-scoped ACL. The indexer sets `acl_object` = the `#sub`-stripped parent while `doc_id` stays sub-precise (indexer.rs:788-795) and embeds whenever `spec.semantic` (indexer.rs:813-817). The pipeline lowers the ACL set from object ids `o.0` (pipeline.rs:522-538) — parent-scoped — which is exactly why `acl_clause` needs the two-field OR. The two paths therefore disagree, violating the no-drift invariant asserted at engine.rs:228-233 and the SRCH-D1 vector-leak-safe property claimed at engine.rs:1017-1024.

**Impact:** For any sub-artifact document carrying an embedding (Knowledge block, issue sub-item): (1) LEAK — under a `NotIds`/`Difference` deny-set on the parent (Difference lowers to And(left, Not(Ids([parent]))) at pipeline.rs:582-588), the lexical path's deny_clause excludes the child because acl_object==parent is in the deny set, but `admits` returns true because the sub-precise doc_id is not literally in the deny set, so the denied child surfaces through `semantic()`/RAG — an agent or user can retrieve passages from documents they are explicitly denied, defeating GDPR-safe-by-construction on the agent-RAG path. (2) RECALL — under an `Ids` allow-set keyed on the parent, `admits(child_doc_id)` is false so the permitted child is silently hidden from semantic search. Root docs are unaffected since acl_object==doc_id.

**Fix:** Make the vector path enforce the identical two-key semantics as `acl_clause`: store `acl_object` on `VectorRecord` and pass BOTH `doc_id` and `acl_object` to the filter predicate (change `admits`, `knn_filtered`, and the HNSW node to carry/consult acl_object), so `Ids`/`NotIds` membership is tested against `doc_id OR acl_object` exactly as the posting-list path does. Add a regression test with a sub-artifact whose acl_object!=doc_id under both an `Ids` allow-set (must surface) and a `NotIds`/`Difference` deny-set on the parent (must NOT surface) across `search`, `search_structured`, and `semantic`.

> _Verifier note:_ Confirmed by reading source: engine.rs:234-245 (`admits` only compares `doc_id` in every arm); engine.rs:534-548 (`acl_clause` iterates [schema.doc_id, schema.acl_object] as Should terms); engine.rs:554-558 (deny_clause reuses acl_clause); vector.rs:154-162 (VectorRecord has only doc_id/embedding/model_ref, no acl_object); vector.rs:487-524 (knn_filtered evaluates visible(&node.record.doc_id)); indexer.rs:729-734 (acl_object_of strips #sub to parent), indexer.rs:788-795 (doc_id sub-precise, acl_object=parent, debug_assert they differ for a sub-artifact), indexer.rs:813-817 (embeds when spec.semantic regardless of sub/root); pipeline.rs:522-538 (Ids/NotIds built from object ids o.0), pipeline.rs:582-588 (Difference → And(l, Not(r))); pipeline.rs:1007 & 1028 (SAME acl_filter passed to both search and semantic). Severity high is correct: a genuine ACL leak on the RAG path, bounded to sub-artifact docs but directly contradicting the code's own stated invariant.

### 2. 🔵 End-user full-text query string is fed raw into Tantivy's QueryParser — query-DSL reinterpretation, field-scoped probing, and parse-error failures

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** correctness
- **Location:** `crates/myelin-search/src/engine.rs:917`

**What:** `search()` builds `QueryParser::for_index(&self.index, vec![self.schema.text])` and calls `parse_query(text_query)` (engine.rs:917-920) on the FT clause text, which originates as the user's raw `Literal::Str` (compiler lowers `text == "..."` to `FtClause.query` unmodified at compiler.rs:560-572; pipeline passes it through at pipeline.rs:1006-1007). Tantivy's QueryParser interprets its own DSL: `field:value` scoping, AND/OR/NOT, +/-, ranges, phrases. Consequences: (a) ordinary text containing `:`, parentheses, or reserved words is either reinterpreted or makes `parse_query` return Err, which is mapped to `IndexError::Engine` at engine.rs:920 and fails the whole search instead of matching the literal text; (b) a user can scope terms at indexed non-body fields — `doc_id` (STRING|STORED|FAST), `acl_object` (STRING|FAST), `indexed_zookie` (STRING|STORED|FAST), and facet columns are all indexed (engine.rs:435-468) hence reachable via `field:value` — to probe values. The ACL MUST clause is still conjoined (engine.rs:922-925) so this is NOT a cross-tenant leak, only oracle-style probing within the viewer's already-visible set. Separately, the compiler cost guard bounds only predicate node count/depth, not a single string literal's length, so an oversized FT literal passes validation and is expanded into a large boolean query.

**Impact:** A user searching for literal strings like `severity:high`, `C++ (parsing)`, or `foo:bar` gets wrong results or a hard error instead of a text match. A curious user can scope terms to internal fields to confirm values of documents already in their allow-set. A crafted multi-megabyte single-literal FT query bypasses the node/depth cost guard and becomes a large term query. All effects are bounded to the viewer's already-visible ACL scope.

**Fix:** Do not expose the raw Tantivy query DSL to end-user text. Either restrict the parser to the body field and escape/strip field-scoping/operator syntax, or tokenize the user text and build a `BooleanQuery` of `TermQuery`s over `schema.text` directly (mirroring the structured-clause construction), so search text is treated as text. Add a length bound on the FT literal so a single oversized literal cannot escape the cost guard.

> _Verifier note:_ Confirmed by reading source: engine.rs:915-925 (QueryParser::for_index over vec![schema.text], parse_query on raw text_query, Err mapped to IndexError::Engine, ACL conjoined as separate Must clause so no cross-tenant leak); compiler.rs:560-572 (Text Eq → FtClause{query: query.clone()}, raw literal, no sanitization); pipeline.rs:1006-1007 (ft.query passed unmodified to backend.search); engine.rs:435-468 (doc_id/acl_object/indexed_zookie/facets all indexed → reachable via `field:` scoping, validating the probing sub-claim). Severity low is correct: the harm is UX breakage plus in-scope oracle probing plus a minor cost-guard bypass, all within the viewer's already-authorized visible set — no privilege boundary is crossed.
