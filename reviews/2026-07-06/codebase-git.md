# Git hosting (myelin-git)

_I deep-read the highest-risk modules of myelin-git: durable.rs (DurableGitRepo — write_blob/write_tree/write_commit, update_ref_cas, reflog_len/reflog_entries, is_fast_forward, fsck, and DurableGitStore::create_repo/repo_path), reconcile.rs (GitRefUpdatedRecord + reconcile_refs), receive_pack.rs (RefStore::receive one-transaction CAS+outbox co-commit, apply_one, seq_of, the per-ref RefLock linearisation, CrashPoint injection), merge_gate.rs (parse_required_context + evaluate_merge_gate/classify_row), gix_backend.rs (RootedResolver::repo_path + validate_path_segment/validate_repo_slug), and pr_store.rs::merge_pr. The path-traversal defense in gix_backend is genuinely strong (fail-closed allowlist per segment, both read and write paths route through the one resolver, cross-tenant `..`/absolute/NUL/backslash all refused with tests). The merge gate is correctly fail-closed (missing/not-green/un-endorsed-fork all BLOCK; trust read off the fact, never recomputed). The receive-pack one-transaction emit-iff-committed model and per-ref lock discipline (sorted multi-ref acquisition, deadlock-free) are sound, and merge_pr correctly advances refs THROUGH ref_store.receive so merges co-emit git.ref.updated. The libgit2 CAS via reference_matching/reference(force=false) is a real on-disk compare-and-swap. HOWEVER the crash reconciler and update_seq generation have a serious design defect: they use the on-disk reflog length as the durable per-ref update_seq, but git discards a ref's reflog when the ref is deleted (the crate's own delete_cas_removes_ref_and_recreate_restarts_generation test asserts reflog_len resets to 1 after delete+recreate). This makes update_seq non-monotonic across a delete and breaks reconcile_refs idempotency/correctness._

**Kept findings:** 2  (🟠 1 high  ·  🟡 1 medium)

---

### 1. 🟠 Crash reconciler uses reflog-length as update_seq; a deleted-then-recreated ref makes recovery abort or silently drop a committed ref move

- **Severity:** high  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** data-integrity
- **Location:** `crates/myelin-git/src/reconcile.rs:145`

**What:** reconcile_refs derives the durable per-ref generation from `repo.reflog_len(&rec.ref_name)` (line 145) and treats `rec.update_seq <= on_disk_seq` as "already applied, skip" and `>` as "un-applied tail, re-apply" (lines 146-150). But git deletes a ref's reflog when the ref itself is deleted — the crate's own durable.rs test `delete_cas_removes_ref_and_recreate_restarts_generation` asserts reflog_len is 1 (not 3) after create→delete→recreate. Because RefStore::seq_of also reads reflog_len (receive_pack.rs:728) and new_seq = prev_seq+1 (receive_pack.rs:911), the update_seq stamped into the committed git.ref.updated events RESTARTS at 1 after any delete. So the committed outbox history for a ref that was deleted and recreated contains e.g. update_seq [1(create c1), 2(update c2), 3(delete), 1(recreate c9)] — two records with update_seq 1, and update_seq 2 that is now GREATER than the live reflog_len of 1. On restart, reconcile_refs replays ALL committed rows (refs_from_outbox uses committed_rows(), line 92). Sorting by update_seq, the recreate(c9, seq 1) collides with the original create(seq 1) and is skipped as "already_current", while update(c2, seq 2) is seen as "behind" (2 > reflog_len 1), attempts a re-apply, reads the live tip c9 which does not equal its recorded old_oid c1, and returns DurableError::CasMismatch (lines 164-174).

**Impact:** The crash reconciler runs on every restart BEFORE the durable store serves the live front door (per the module doc). A perfectly healthy repo whose branch was ever deleted and recreated will make reconcile_refs return CasMismatch and abort recovery, or — in the burst-crash ordering — silently skip the committed recreate and leave the ref DELETED instead of pointing at the committed tip. That is exactly the silent-loss-of-a-committed-ref-move this reconciler exists to prevent. The same reset also defeats update_seq as the outbox ordering tiebreak (arch §3): two distinct git.ref.updated events for one ref carry update_seq 1, so downstream consumers cannot order the recreate after the original create.

**Fix:** Do not use reflog_len as the durable update_seq. Persist a monotonic per-ref generation that never decreases across delete (e.g. a dedicated durable counter/row keyed by (repo, ref) that survives ref deletion, matching the frozen git_ref/git_reflog DDL's update_seq column rather than the physical reflog file length). Reconcile idempotency must key on that never-reset generation and on the recorded old_oid→new_oid chain, not on reflog entry count. Add a reconcile test that replays a committed create→update→delete→recreate history and asserts convergence + idempotent re-run without CasMismatch.

> _Verifier note:_ Every cited link verified. reconcile.rs:145 derives on_disk_seq from repo.reflog_len(); :146-150 treat update_seq<=on_disk_seq as skip, > as re-apply. The stamped update_seq comes from receive_pack.rs:910-911 (new_seq = seq_of()+1) where seq_of() on the Disk backing is repo.reflog_len (:728), and :936 emits update_seq:new_seq into git.ref.updated. durable.rs test at :1075-1096 proves reflog_len RESTARTS at 1 after create->delete->recreate, so committed update_seqs for such a ref are [1(create),2(update),3(delete),1(recreate)]. refs_from_outbox (reconcile.rs:90-97) replays ALL committed_rows for the repo; sort_by_key is stable so the two seq-1 rows keep outbox order. ### 2. 🟡 update_ref_cas mutates shared on-disk repo config (user.name/user.email) on every ref update, racing parallel pushes and mislabeling the reflog pusher pseudonym

- **Severity:** medium  ·  **Verdict:** 🟨 PLAUSIBLE  ·  **Category:** concurrency
- **Location:** `crates/myelin-git/src/durable.rs:337`

**What:** Each update_ref_cas writes the committer pseudonym into the repo's on-disk config via cfg.set_str("user.name"/"user.email", committer_pseudonym) (lines 337-343) and then relies on libgit2 reading that config to stamp the reflog committer. By design (GIT-P10 / receive_pack.rs per-ref RefLock), pushes to DIFFERENT refs of the same repo proceed in PARALLEL — they take different in-process RefLocks but share the same on-disk DurableGitRepo path. Two parallel update_ref_cas calls therefore concurrently rewrite the single shared .git/config user.name/user.email. There is no lock coordinating the config write with the subsequent reference_matching that reads it back for the reflog signature.

**Impact:** Two failure modes under concurrent pushes to different refs: (1) libgit2 config lockfile contention can surface as a spurious DurableError::Git failing an otherwise valid push; (2) more insidiously, thread A sets user.name=A, thread B overwrites it with B, then A's reflog entry records committer B — the durable reflog attributes A's ref move to the wrong tenant pseudonym (a GIT-1 pseudonymity/attribution violation). Because reconcile_refs replays the reflog committer as pusher_pseudonym (reconcile.rs reads e.committer), a mislabeled committer also propagates a wrong pseudonym into any recovered event.

**Fix:** Do not stamp identity through mutable repo config. Set the committer signature explicitly per operation using the libgit2 reflog-signature API (e.g. pass a git2::Signature to the reference update / use Repository with an explicitly supplied committer) so the pseudonym is bound to that specific ref update rather than to shared global config state, eliminating the cross-ref race.

> _Verifier note:_ The structural race is confirmed in source. durable.rs:337-343 sets user.name/user.email into repo.config() (the shared on-disk .git/config) on every update_ref_cas, then relies on libgit2 reading it back to stamp the reflog committer (:358 reference / :364 reference_matching); reflog_entries (:427-431) reads that committer back, and reconcile.rs replays it as pusher_pseudonym. receive_pack.rs:861-882 + type RefLock (=Mutex<()>, :535) confirm pushes to DIFFERENT refs of one repo take DIFFERENT locks and proceed in PARALLEL, and no repo-level lock guards the config write — so two concurrent update_ref_cas calls do race the single shared .git/config with no coordination. Downgraded from CONFIRMED to PLAUSIBLE only because the concrete harm depends on libgit2 runtime internals not visible in this repo: (1) whether concurrent config.lock writes surface as a spurious DurableError::Git, and (2) whether A's reference op re-reads B's config value for the reflog signature (config-refresh/cache semantics). The anti-pattern (binding per-op identity to mutable shared global config) and the unsynchronized parallel window are real; severity medium is appropriate. Recommendation to pass an explicit git2::Signature per op is sound.
