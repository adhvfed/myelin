# Identity, access & tenancy (myelin-identity-service, myelin-identity, myelin-tenancy)

_I deep-read the security-critical paths across all three crates. myelin-tenancy/src/lib.rs is a small, sound value-type crate: TenantId/Region/ResidencyTag are opaque, PII-free, construction-restricted (no From<String>), and CrossCellPointer is a frozen 4-field PII-free frame — no logic to break. myelin-identity/src/lib.rs is a frozen contract ABI (Principal, IdentityService, SetExpr, CaveatContext, PseudonymHandle) with fail-closed stub bodies; PseudonymHandle::new/parse correctly reject grammar-breaking tokens. In myelin-identity-service I focused on the real crypto and authz logic: capability_crypto.rs (PASETO v4.public Ed25519 via ring, macaroon HMAC caveat chain with monotone-attenuation + constant-time ct_eq, DPoP RFC-9449 with sender-constraint/freshness/replay) is carefully total-over-attacker-bytes; oidc.rs (OidcVerifier) pins alg from the JWKS key not the header, rejects alg:none and HS* confusion via byte-safe get(..2), verifies iss/aud/exp with saturating arithmetic, and reads tenant only from verified claims (ID-3); saml.rs (SamlVerifier + parse_xml/canonicalize) is an unusually rigorous hand-built XSW defence (single-assertion, single-signature enveloped-child, unique-ID reference pinning, DTD/entity/comment/PI rejection, injected trust anchor never document KeyInfo). authenticate.rs/machine_auth.rs enforce tenant-from-credential/token, per-kind authority ceilings (deploy-key repo-scope, per_job self-hosted one-tenant), monotone Authority::attenuate intersection, and durable revocation consult. revocation.rs compares expiry by instant (now_strictly_before) fail-closed, mirror-first idempotent writes. check_engine.rs is depth-bounded, memoised, fail-closed. The unit is genuinely high-quality and heavily mutation-tested; the findings below are the residual issues I could substantiate, the most material being CheckEngine::object_id_of collapsing an ArtifactRef to its last path segment (type-blind authorization)._

**Kept findings:** 3  (🟡 1 medium  ·  🔵 2 low)

### 1. 🟡 check(): object identity for authorization discards the subsystem/type, enabling cross-artifact authz confusion

- **Severity:** medium  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** authorization
- **Location:** `crates/myelin-identity-service/src/check_engine.rs:363`

**What:** `object_id_of` reduces the `check` object `ArtifactRef` to only the final `/`-segment: `myelin://acme/issues/issue/PROJ-1` and `myelin://acme/git/repo/PROJ-1` both yield the bare id `PROJ-1`, discarding the subsystem (`issues`/`git`) and type (`issue`/`repo`). The tuple store (tuple_store.rs ~line 173/432) keys grants on the raw `RelationTuple.object.0` string. Because the authorization decision matches on this type-blind trailing id within a `(tenant, region)` partition, a grant tuple recorded for one object authorizes any other object of any type in the same tenant that shares the same trailing id and is checked with the same relation name (e.g. a generic `reader`). Separately, the reduction is inconsistent: a full-URN ref yields `PROJ-1` while a bare ref like `repo:core` is kept whole, so a tuple written as `issue:PROJ-1` will silently never match a URN check for the same object.

**Impact:** Within a tenant, a subject legitimately granted a relation on one artifact can be authorized against a different artifact (different subsystem/type) that shares the trailing id — a cross-artifact privilege-confusion / fail-open on the core `check` decision path (StoreBackedCheck). Conversely, id/URN-form mismatches cause silent over-denial (availability). Exploitability depends on the write path minting type-local (colliding) object ids, which is plausible for subsystem-local numeric ids.

**Fix:** Authorize on the full type-qualified object identity, not the last path segment. Key tuples and derive the check id from the same canonical `(subsystem, type, id)` tuple (or the full normalized `myelin://` ref) so `issue/PROJ-1` and `repo/PROJ-1` are distinct authorization objects, and so a URN ref and the stored tuple id are guaranteed to agree.

> _Verifier note:_ Verified object_id_of (check_engine.rs:363-376): it strips a #sub anchor then takes root.rsplit('/').next(), so a full URN myelin://acme/issues/issue/PROJ-1 reduces to the type-blind 'PROJ-1'. The in-tree test object_id_extracted_from_urn_and_sub_anchor (lines 1168-1183) proves the exact inconsistency the finding claims: the URN -> 'PROJ-1' but a bare 'repo:core' (no '/') is kept whole. check() (line 159/175) and direct_subjects() (line 210/217) both authorize on this reduced id, and SnapshotView.by_object is keyed on the raw tuple object string (check_engine.rs:243; tuple_store.rs:173 hash, :208 partition, :380, :432). So the decision IS type/subsystem-blind within a (tenant,region) partition. The over-denial half is concretely confirmable: a URN check reducing to a trailing id will silently miss a type-prefixed stored tuple (git writes ids like 'ref:repo:core::/glob' and 'repo:core' per git_fragment.rs:253 and the tests) -> fail-closed mismatch. The cross-artifact fail-open half is real in principle but conditional on the write path minting bare, un-type-prefixed colliding ids across two subsystems; the demonstrated convention in-tree (repo:core, ref:...) is type-prefixed and would mismatch (over-deny) rather than confuse, so live fail-open exploitability could not be fully confirmed from source. The underlying defect (type-blind + inconsistent normalization on the core check path) is real; medium is fair.

### 2. 🔵 SSO verifiers default to a per-instance in-memory replay guard; per-request construction defeats OIDC/SAML/DPoP replay defence

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** replay-protection
- **Location:** `crates/myelin-identity-service/src/oidc.rs:327`

**What:** `OidcVerifier::new` (oidc.rs:327), `SamlVerifier::new` (saml.rs:837) and `PasetoCapabilityVerifier::new` (capability_crypto.rs:635) each construct a fresh, private `ReplayGuard`/`DpopReplayGuard` backed by an in-process `Arc<Mutex<BTreeSet>>`. Replay protection therefore only holds when the exact same verifier instance sees both presentations. Sharing across instances requires the composition root to remember to call `with_replay_guard(shared)`. Additionally the seen-set is never evicted, so it grows unbounded for the lifetime of the guard.

**Impact:** If the production wiring builds a verifier per request/worker (or per key rotation) without explicitly injecting a shared guard, a captured OIDC id-token / SAML assertion / DPoP proof can be replayed against a different instance. The unbounded seen-set is also a slow memory-growth DoS. Both are latent until the real verifiers are wired (production currently routes SSO schemes to RefuseUnsupportedVerifier), so this is a footgun rather than a live bug today.

**Fix:** Make the shared replay store a required constructor argument (or default to a process-wide singleton), and back it with a TTL-bounded store so the guard is both correct across instances and bounded in size. Add a wiring test asserting two verifier handles reject a cross-handle replay by default.

> _Verifier note:_ Verified OidcVerifier::new (oidc.rs:323-330) builds replay: ReplayGuard::new(); SamlVerifier::new (saml.rs:834-840) and PasetoCapabilityVerifier::new (capability_crypto.rs:629-637) do the same with DpopReplayGuard::new(). Each guard is a private Arc<Mutex<BTreeSet<String>>> (oidc.rs:222-223, capability_crypto.rs:478-479) and check_and_record only inserts, never evicts (oidc.rs:234-237) -> unbounded seen-set confirmed; the oidc.rs:220 doc comment itself says the durable defence (token TTL / Redis-class store) is out of scope. Sharing requires an explicit with_replay_guard(...) call (oidc.rs:333, saml.rs:843, capability_crypto.rs:652). Confirmed the production default routes OIDC/SAML to RefuseUnsupportedVerifier (authenticate.rs:335-340, test at :950-965), so the real verifiers are not wired today -> this is a latent footgun, not a live bug, exactly as the finding self-assesses. Low is correct.

### 3. 🔵 Credential resolution partitions by (tenant, region) in-memory but by tenant only on the PG backend

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** consistency
- **Location:** `crates/myelin-identity-service/src/principal_store.rs:741`

**What:** `resolve_credential`/`link_credential` key the in-memory backend on `part_key = (tenant, region)` (principal_store.rs:748/827), but the `#[cfg(feature="integration")]` PG backend passes only `scope.tenant().0` (lines 766/721), dropping the region component of the partition key. The two backends thus have different partition granularity for the same API.

**Impact:** No cross-tenant leak (tenant is still enforced), but a tenant with principals/credentials in more than one region resolves differently under PG vs in-memory: a PG lookup could return a link written under a different region of the same tenant, whereas the in-memory model would not. Given Region is normally immutable-per-tenant this is unlikely to bite, but it is a real semantic divergence between the model and the durable system-of-record and could mask region-scoping regressions in tests.

**Fix:** Include the region in the PG credential-link key (or explicitly document and test that S1 credential links are tenant-scoped, region-agnostic, and make the in-memory backend match) so the model and durable backend agree byte-for-byte on the partition.

> _Verifier note:_ Verified part_key(scope) = (tenant, region) (principal_store.rs:827-829). The in-memory arm of resolve_credential keys on this full part_key (line 748, then :754/:759) and link_credential likewise (.entry(part_key) at :710). The #[cfg(feature="integration")] PG arm passes only &scope.tenant().0 to backing.link_credential (line 721) and backing.resolve_credential (line 766), dropping the region component. So the two backends have different partition granularity for the same API — confirmed at the call boundary. No cross-tenant leak (tenant is still enforced on both). The concrete impact (a PG resolve returning a link written under a different region of the same tenant) depends on the unseen myelin_storage durable backing's internal keying, which I could not inspect, so that downstream effect is plausible rather than fully proven; but the source-level divergence the finding describes is real. Low is correct.
