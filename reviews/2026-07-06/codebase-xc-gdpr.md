# Cross-cutting: personal-data lifecycle & erasure

_The GDPR personal-data lifecycle is unusually mature and mostly fail-closed: the classify-derive macro forces a five-tag classification (and compile-errors on untagged PII-named fields), the search pipeline conjoins an ACL pre-filter with a tenant-mismatch guard and a stale-reverse-index watermark (no silent widen to All), the retention tightest-policy-wins/legal-floor merge is correct, the transfer gate denies extra-EU by default with fail-closed EEA membership, the legal-hold gate is fail-safe-to-suspend, and the event-bus/git holders model post-restore re-erasure and pseudonymous-by-default commit authorship. No PII was found leaking into logs, errors, or audit/receipt content-addresses. The main defect is that the DSR completion boundary does not enforce its own stated invariant: verify() transitions to Verified on a caller-supplied receipt list without reconciling it against the data-map-resolved checklist, so a mapped holder absent from the hand-assembled registered-holder set is silently skipped while coverage telemetry reads 100% — the 'forgot the search index' escape the architecture claims to foreclose. A related lower-severity gap: the git DSR receipt hardcodes its holders-hit set rather than deriving it from evidence, making its green gate tautological. Most of the erasure surface is still explicitly on in-memory 'floor' models with live store bindings deferred to later milestones, so these are latent-but-structural rather than currently-exploitable-in-prod._

**Kept findings:** 2  (🔵 2 low)

---

### 1. 🔵 DSR completion never reconciles collected receipts against the data-map-resolved checklist — a mapped-but-unregistered holder is silently skipped while the DSR reports green

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** gdpr
- **Location:** `crates/myelin-gdpr-service/src/dsr.rs:644`

**What:** Two independent holder sets exist and are never reconciled. (a) dsr.checklist is resolved from the data-map Inventory in fan_out() (dsr.rs:633, resolve_checklist_from_map over inventory.holders). (b) The fan-out runs over UpstreamHolderOrchestrator.holders — the hand-passed register_m1_upstream Vec. FanOutDriver::drive (fanout.rs:493) fans over set (b) and calls dsr.verify(id, receipt_strings) with receipts derived only from set (b). verify() (dsr.rs:644-653) does only transition(dsr, Verified) + dsr.receipts = receipts — it never compares the receipts against dsr.checklist. erasure_fanout_coverage (orchestration.rs:347-352) is done_count/holders.len(), both over set (b). So a holder present in the data-map checklist but absent from the registered set is never verified and never lowers coverage. The DsrState doc at dsr.rs:181 ("the machine CANNOT leave AwaitingHolders for Verified until every checklist holder is receipted") overstates an invariant the code does not enforce.

**Impact:** If a struct's owning store appears in the generated data-map roster but is omitted from register_m1_upstream, the DSR completes Verified->Completed with a green certificate and 100% coverage telemetry while that holder was never driven. Impact is fully latent today: the live PersonalDataHolder bindings are in-memory floor models, and whole-data-map coverage is an explicitly-named future floor (M5 / P-GA-32, orchestration.rs:246-248). The missing reconciliation is what would make a future omission silent rather than loud.

**Fix:** When the live bindings and whole-map coverage (P-GA-32) land, reconcile the collected receipt holder-ids against dsr.checklist in verify() (or in drive() before verify): fail with a typed DsrError if any checklist holder lacks a receipt, and derive the coverage denominator from the data-map checklist rather than the registered-holder count. Note that closing this also requires unifying the two holder-id namespaces (the data map uses `<kind>:<name>` e.g. `search_index:search_index`; the registered set uses bare ids e.g. `identity`/`blob_store`), so it is genuine design work, not a one-line check. Also correct the dsr.rs:181 doc so it does not claim an enforced invariant that only lands at M5.

> _Verifier note:_ Confirmed by reading dsr.rs verify()/fan_out(), fanout.rs drive(), and orchestration.rs fanout_coverage(). The divergence is demonstrable in the existing passing test drive_fans_out_data_map_driven_and_seals_a_verifiable_receipt (fanout.rs:727): checklist = {identity, search_index:search_index} (2), registered set = 6 upstream holders, DSR completes green with coverage 1.0 and search_index:search_index never driven. Downgraded medium->low because the concrete PII-survival impact is entirely latent behind in-memory floor models and is explicitly deferred to the named M5/P-GA-32 gate (the M1 floor is documented as '100% of existing/registered holders', orchestration.rs:246-248); the current code matches its documented floor. The only defect active today is the overstated dsr.rs:181 doc comment.

### 2. 🔵 Git DSR receipt hardcodes holders_hit = GitHolder::ALL instead of deriving it from the storage orchestrator's evidence, so is_green()/missed_holders() structurally cannot detect a skipped crypto-shred holder

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** gdpr
- **Location:** `crates/myelin-git/src/holder.rs:362`

**What:** GitErasureFanOut::erase_fanout (holder.rs:322) drives the storage CryptoShredErase orchestrator then sets `let holders_hit = GitHolder::ALL.to_vec();` unconditionally (holder.rs:362). is_green() (holder.rs:236-243) and missed_holders() (holder.rs:246-252) both test whether holders_hit contains every GitHolder::ALL member, which is tautologically true because holders_hit was just assigned ALL. Only the CacheCdn leg is independently evidenced (via the invalidated/missing vecs, holder.rs:348-357). The attestation that steps 1/2/2b/3/4/5/6 each reached their holder is asserted, not derived from storage_receipt.

**Impact:** The 'GIT-D2 green: 0 holders missed' proof is self-fulfilling for the crypto-shred holders. Sound today, but the defence-in-depth NotGreen gate (holder.rs:400) cannot catch a skipped crypto-shred holder: a future change that tolerates a missing sub-holder would yield a falsely-green git DSR receipt with no assertion catching it.

**Fix:** Have CryptoShredErase::erase report which holders/steps it actually drove (e.g. a covered-set or per-step receipts in ErasureReceipt) and construct holders_hit from that evidence, so is_green()/missed_holders() reflect what the fan-out actually reached rather than a hardcoded full set.

> _Verifier note:_ Confirmed the hardcoded assignment (holder.rs:362) and the tautological checks (holder.rs:236-252). Verified the 'sound today' premise directly: EraseHolders (erase.rs:172-189) declares pseudonym/search/refs/bus/ledger as non-Option `&dyn` seams; CryptoShredErase::erase (erase.rs:327-395) `?`-propagates every step (340,358,362,365,368), so an Ok return implies every crypto-shred holder ran. git_reach is the only Option and is separately fail-closed in erase_fanout (holder.rs:331, GitStructureReachNotWired). So holders_hit=ALL is currently justified by the Ok result; the finding is a genuine latent defensive-coding gap. Severity low is correct.
