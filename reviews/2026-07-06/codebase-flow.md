# Flow engine (myelin-flow)

_I reviewed myelin-flow's durable-workflow core in depth: the replay/lease engine (engine.rs — drive_full, RunStore::lease_runnable/settle/wake, SignalStore::deliver/first_unconsumed_for/consume, FlowTelemetry), the WfCtx surface and journal co-commit (wfctx.rs — WfCtx::activity's replay short-circuit + divergence latch, now/rand side-markers, sleep_until, wait_for_signal, commit, WfJournal::commit_rows with the signal_waited→signal_received upgrade), the minute-bucket timer wheel (timer.rs — TimerStore::arm/scan_due/fire/re_arm/disarm, TimerWheel::tick, epoch_minute), the reserve/settle bookend (budget.rs — Wallet, BudgetGate::reserve/begin/settle, WfCtx::metered_activity), loop safety (loopsafety.rs — CausalGuard::admit_child/admit_activity), the control plane (executor.rs — FlowExecutor::start/signal/describe/cancel, partition_for), the inbound signal consumer (signal_consumer.rs — FlowSignalConsumer), and the merge-queue body (merge_queue.rs — run_merge_attempt, decode_ci_result). The replay/idempotency machinery is genuinely careful: the UNIQUE(tenant,run_id,command_id) journaling is idempotent, the P-FLOW-07 kind-divergence guard latches and halts instead of double-effecting, timer fire is effectively-once via set-fired + idempotent journal, and SignalStore::deliver models ON CONFLICT DO NOTHING correctly. The defects I found cluster around effects that are applied OUTSIDE the FLOW-D5 journal/outbox co-commit transaction (signal consume, budget ledger mutations), which contradicts the crate's own atomicity invariant, plus a concrete budget-reservation leak on activity exhaustion. Overall the engine is well-constructed; the findings are targeted integrity/durability gaps rather than pervasive problems._

**Kept findings:** 5  (🟠 1 high  ·  🟡 3 medium  ·  🔵 1 low)

### 1. 🟠 metered_activity leaks its budget reservation forever when the inner activity exhausts its retries

- **Severity:** high  ·  **Verdict:** 🟨 PLAUSIBLE  ·  **Category:** resource-leak
- **Location:** `crates/myelin-flow/src/budget.rs:454`

**What:** In `WfCtx::metered_activity`, a fresh dispatch does `gate.reserve()` (which DEBITS the wallet's `available` balance, budget.rs:277) then `gate.begin()` (marks the reservation InFlight), then `let result = self.activity(policy, f)?;`. If the inner activity exhausts its retry budget it returns `WfError::ActivityExhausted`, and the `?` propagates BEFORE the `gate.settle(...)` at line 460 ever runs. The reserved `cost` therefore stays debited from the wallet and the reservation stays permanently InFlight with no refund. The `ledger_run` key is derived internally from `dispatch_command_id` (`dispatch_ledger_run`, budget.rs:381) and is never exposed to the workflow body, so the body CANNOT settle or release it either — contradicting the code comment at 452-453 that claims "it settles when the body settles it." On crash-recovery re-drive the reserve hits `DuplicateReservation` (fresh=false), so begin/settle are skipped and the leak is never reconciled.

**Impact:** Every metered activity that exhausts retries (e.g. a flaky CI dispatch inside run_merge_attempt, or any metered_schedule_and_run_job) permanently and irreversibly reduces the run's wallet by the reserved amount. Repeated transient failures within a run compound the loss until the wallet is exhausted and the self-limiter (BudgetGate::reserve) starts refusing ALL further dispatches — a run can starve its own budget purely from transient activity errors, with no recovery path. This is a budget-integrity/resource-leak bug and is untested (all metered_activity tests use succeeding closures except the empty-wallet case which never reserves).

**Fix:** On the activity-exhaustion path, settle the reservation with zero/actual metered units (refunding the full over-reservation) before propagating the error, or wrap the `self.activity(...)?` so a failure calls `gate.settle(&tenant, &ledger_run, &[])` (or an explicit release) on the fresh drive. Add a test asserting the wallet balance is restored after a metered_activity whose closure exhausts.

### 2. 🟡 metered_activity leaks its budget reservation on activity exhaustion

- **Severity:** medium  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** resource-leak
- **Location:** `crates/myelin-flow/src/budget.rs:454`

**What:** In WfCtx::metered_activity (budget.rs:399-469), on the fresh drive the gate.reserve() at line 423 debits the wallet by `cost` (Wallet debit happens in BudgetGate::reserve, budget.rs:277-279) and gate.begin() at line 445 moves the reservation to InFlight. The inner activity then runs at `let result = self.activity(policy, f)?;` (line 454). When the activity exhausts its retries, WfCtx::activity stages an `activity_failed` history row and returns WfError::ActivityExhausted (wfctx.rs:919-922). The `?` on line 454 propagates that error, so control returns BEFORE the settle block at lines 459-463. The reservation therefore stays InFlight: the wallet is never credited back (no gate.settle -> no refund of `cost`), and NO cost event is recorded for the failed dispatch, so the wallet is debited with no corresponding billed cost. The doc comment at lines 450-453 claims 'it settles when the body settles it,' but there is no reachable settle mechanism: metered_activity returns WfResult<Vec<ArtifactRef>> and never yields the ledger_run; dispatch_ledger_run() (line 381) and budget() (wfctx.rs) are pub(crate) and metered_activity does not return the ledger_run, so an out-of-crate workflow body cannot reconstruct the key or reach BudgetGate::settle. On a re-drive the activity replays deterministically to activity_failed (wfctx.rs:848-854) and the reserve hits the DuplicateReservation guard (fresh=false), so the reservation remains permanently InFlight with no refund and no cost event.

**Impact:** Each metered activity whose closure exhausts its retries permanently loses its full `cost` reservation from the per-run wallet, with no billed cost event recorded — an accounting inconsistency (wallet depleted, nothing billed). A run that continues issuing further metered dispatches against the same wallet after catching such failures would cumulatively drain the wallet until all subsequent dispatches are Refused, despite no real spend — a self-inflicted denial of dispatch.

**Fix:** On the exhaustion path, settle the reservation (e.g. with zero/actual metered units) before returning the error so the over-reservation is refunded and a cost event is recorded, or otherwise release the InFlight reservation; alternatively expose the ledger_run so the body can settle/compensate as the doc claims.

> _Verifier note:_ Read budget.rs:1-469 (Wallet debit in reserve at 277-279; settle/refund at 319-336; metered_activity at 399-469 with the ?-before-settle at 454; doc comment 450-453 acknowledging the InFlight-on-exhaustion behavior and claiming 'it settles when the body settles it'). Read wfctx.rs:822-923: activity() journals activity_failed and returns WfError::ActivityExhausted on retry exhaustion, and replays to the same failure with 0 re-execution. Confirmed dispatch_ledger_run (381) and budget() are pub(crate) and metered_activity does not return the ledger_run, so the settle key is not exposed to external bodies. Confirmed no test exercises the metered-activity-closure-exhaustion path: budget.rs tests cover reserve-refused (567), successful settle (603), and second-dispatch-refused (635), but none assert wallet/reservation state after the activity itself exhausts. Severity lowered from high to medium: the per-reservation leak and missing cost event are real and confirmed, but the 'drain until all dispatches refused' scenario requires a consumer that catches metered_activity exhaustion and keeps issuing metered dispatches against the same wallet within one run's lifetime; the only current metered_activity consumer, merge_queue.rs run_merge_attempt (402), propagates the error via `?` (the ActivityExhausted catch at merge_queue.rs:486 is on a separate non-metered `activity` at step 3), so no in-product consumer currently loops metered dispatches — the run terminates and the per-run wallet is discarded, limiting today's blast radius. Also noted the production Commercial-wallet binding is not yet wired (P-ST-19), so no real money is currently affected.

### 3. 🟡 wait_for_signal consumes the durable signal buffer outside the FLOW-D5 co-commit, risking a permanently-stuck run on a crash between consume and commit

- **Severity:** medium  ·  **Verdict:** 🟨 PLAUSIBLE  ·  **Category:** durability
- **Location:** `crates/myelin-flow/src/wfctx.rs:1256`

**What:** The whole crate's premise (FLOW-D5) is that a workflow step's journal row + outbox emit become durable together in `WfCtx::commit`, and "a WfCtx dropped without commit writes NOTHING." But in `wait_for_signal`, `signals.consume(&self.tenant, &self.run_id, name, &idem_key, received_seq)` (wfctx.rs:1256) mutates the shared durable SignalStore EAGERLY, during body execution, and its boolean return is ignored. The corresponding `signal_received` journal row is only STAGED (stage_received, 1261) and is not made durable until the later `WfCtx::commit`. So the consume (modeled as `UPDATE wf_signal SET consumed_seq=... WHERE consumed_seq IS NULL`) is NOT part of the journal/outbox transaction the architecture §4.3 requires it to share. If the drive dies (or diverges → `drop(ctx)` without commit at engine.rs:1233) after consume but before commit, the signal is marked consumed while no `signal_received` row records it. On re-drive, replay sees only the `signal_waited` marker, falls through to the live buffer re-check, and `first_unconsumed_for` skips the now-consumed row — so the wait re-parks forever waiting for a signal that was already (silently) consumed.

**Impact:** Lost signal + permanently stuck (waiting) run — precisely the exactly-once/atomicity property the crate claims to guarantee. In the pure in-memory harness both stores are lost together on process death so tests can't observe it, but the module docs promise dev↔prod is a config swap where SignalStore=wf_signal (durable) and journal=wf_history (durable); under that binding the eager-consume-then-deferred-journal is a dual-write that breaks consume-exactly-once and can wedge a HITL/merge-queue run indefinitely.

**Fix:** Stage the consume as part of the co-commit rather than applying it eagerly: carry the `(name, idem_key, consumed_seq)` in the WfCtx and perform `SignalStore::consume` inside `WfCtx::commit` in the same logical transaction as `journal.commit_rows`, so consume + signal_received become durable atomically (or are both discarded on abort). At minimum, check the ignored return of `consume()` and treat a lost race as a re-park rather than a spurious Signalled.

> _Verifier note:_ Structural claim CONFIRMED in source: wfctx.rs:1256 calls `signals.consume(...)` eagerly during body execution and ignores its bool return; the matching `signal_received` row is only STAGED via stage_received (1261) and pushed to consumed_signals (1257). WfCtx::commit (1472-1490) moves out only tx/journal/staged_history/staged_attempts and re-applies NOTHING to `signals` — so consume is genuinely outside the journal/outbox co-commit. SignalStore::consume (engine.rs:491-511) mutates a shared Arc<Mutex<HashMap>> in place (models `UPDATE … SET consumed_seq WHERE consumed_seq IS NULL`), and first_unconsumed_for (462-481) filters `consumed_seq.is_none()`, so a consumed-but-unjournaled row IS skipped on re-scan — the re-park mechanism the finding describes is real. HOWEVER the claimed catastrophic impact (permanently stuck `waiting` run) is NOT confirmable from source alone: SignalStore here is a pure in-memory Arc<Mutex<HashMap>>, so a process crash loses the signal store and journal together atomically — the dual-write hazard only bites under the promised durable swap (SignalStore=wf_signal, journal=wf_history) which is not wired in this crate. The one in-process manifestation is the divergence path (engine.rs:1231-1245): a body that diverges AFTER consume drops ctx without commit, silently losing the consumed signal — but that run is dead-lettered NONDETERMINISTIC (terminal), so it does not 're-park forever', it just loses the signal. Verdict PLAUSIBLE: the eager-consume-outside-co-commit and ignored return are confirmed facts and a genuine architecture-violating dual write, but the headline stuck-run impact depends on durable wiring not present in-source. Severity medium is fair.

### 4. 🟡 Budget reserve/begin/settle mutate the durable ledger outside the co-commit, so a failed commit can leave the ledger debited while the journaled effect is discarded

- **Severity:** medium  ·  **Verdict:** 🟨 PLAUSIBLE  ·  **Category:** data-integrity
- **Location:** `crates/myelin-flow/src/budget.rs:443`

**What:** Same class of dual-write as the signal-consume finding, on the money path. In `metered_activity`, `gate.reserve()` (debits the wallet), `gate.begin()`, and `gate.settle()` (refunds) all mutate the durable CostLedger/Wallet immediately during body execution, entirely separate from `WfCtx::commit`'s journal/outbox transaction. The inner `self.activity(...)` only STAGES its `activity_completed` history row. If `WfCtx::commit` subsequently fails (drive_full settles the run FAILED, engine.rs:1267-1270) or the process crashes after settle but before commit, the ledger has recorded reserve→begin→settle while the activity's journal row is never committed. On re-drive, the activity is NOT journaled so its closure RE-EXECUTES (a real double side-effect the crate claims is impossible), while the reserve returns DuplicateReservation and the ledger is never re-progressed — a divergence between the money ledger and the workflow journal.

**Impact:** The reserve/settle ledger and the wf_history journal can disagree after a crash/failed commit: a re-executed (double) activity side-effect paired with a ledger that thinks the dispatch already settled, or vice-versa. This undermines both the "0 double-effect" (FLOW-D1) and the reserve/settle accounting guarantees when the co-commit is not atomic with the ledger writes.

**Fix:** Either make the reserve/settle ledger writes participate in the same transaction as the WfCtx co-commit (stage them and apply in commit()), or key the activity's journaling and the ledger progression off the same atomic boundary so a re-drive cannot re-execute the closure while the ledger believes it settled. Document explicitly if the ledger is intended to be a separate transactional domain, and reconcile the replay path accordingly.

### 5. 🔵 Shared-root loop-safety tally never ages out, so long-lived correlation roots eventually trip the tripwire and drop legitimate workflows

- **Severity:** low  ·  **Verdict:** ✅ CONFIRMED  ·  **Category:** correctness
- **Location:** `crates/myelin-flow/src/loopsafety.rs:121`

**What:** `CausalGuard::admit_child` is documented (loopsafety.rs:20-24, 49-54) as a SLIDING-WINDOW tripwire: past `shared_root_cap` starts sharing one correlation_id "within the window" the breaker trips. But `GuardInner::root_starts` is a `HashMap<String,u32>` that is only ever incremented (line 206) and never decremented or aged — there is no window/time dimension at all. The count for a correlation_id grows monotonically for the entire lifetime of the guard. The code comment at 120 concedes "the engine's window is the run-of-the-loop; a real cell ages it out," i.e. the aging is unimplemented.

**Impact:** A legitimate long-lived correlation root that accumulates `SHARED_ROOT_WINDOW_CAP` (64) child starts slowly over time — not in an adversarial burst — is dropped as if it were a workflow→event→workflow loop, and can never recover because the tally never decays. The tripwire cannot distinguish a slow legitimate fan from a tight loop; it only measures cumulative count, not rate/window.

**Fix:** Implement the actual sliding window (e.g. a timestamped ring/deque per root pruned to the window on each admit, or a periodically-reset epoch counter) so the tally reflects starts-per-window rather than starts-ever, and add a test that a root under the cap-per-window but over the cap-cumulatively is still admitted.

> _Verifier note:_ CONFIRMED in source. GuardInner.root_starts is HashMap<String,u32> (loopsafety.rs:121). admit_child is the ONLY writer: it reads `seen` (196), trips if `seen >= shared_root_cap` (197-203), else inserts `seen+1` (204-206). There is no decrement, no timestamp, no prune, no reset anywhere — grep shows release_activity (236-239) decrements activities_in_flight but there is NO counterpart for root_starts. So the tally is strictly monotonic for the guard's lifetime, contradicting the doc/comments that call it a 'sliding window' (20-24, 49-54) — the comment at 120 openly concedes 'a real cell ages it out', i.e. aging is unimplemented. The guard is a long-lived shared handle (Arc<Mutex>, held e.g. in myelin-agent-service/src/loop_guards.rs:308 for the guard's whole lifetime), so a legitimate root accumulating SHARED_ROOT_WINDOW_CAP (64) cumulative starts is dropped as a loop and never recovers. Impact is real. Severity low is appropriate: it is genuinely a correctness gap but requires 64 cumulative same-root starts and is explicitly acknowledged as a simplified model (the guard's lifetime IS the window), and in myelin-flow the guard is exercised only via drills/re-use, not the core drive loop.
