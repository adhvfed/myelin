## Canon every prompt in this file assumes (the shared reading set)

Each prompt re-states the precise subset it needs, but all assume the M0 substrate from
[`../00-ledger-overview.md`](../00-ledger-overview.md) §6: the Cargo workspace + the eight glue crates, the
`serve(AppSpec)` harness (three ports, holder auto-registration via contract 1.4, ResilientClient, FailStatic,
the protected-human-lane shed order), the transactional outbox + the EventHandler/consumer template, the twelve
committed lints, the contract-coverage scanner, and the failure-injection harness (the 1x/10x/30x load

1.8). A prompt's GATE/DRILLS rows are scenarios on that harness; a prompt's DEFINITION OF DONE requires all
twelve committed lints green and the contract-coverage scanner passing.

**The implementation crate.** GDPR/Audit's runtime code lands in two places. (a) The glue crate **myelin-gdpr**
(ADR-01, a compile-time contract carrier) holds the cross-crate trait shapes every store and consumer compiles
against: the `PersonalDataHolder` trait, the `#[personal_data(...)]` classify-derive + the five-tag enum, the
`SubjectRef`/`TenantId`/`EraseScope`/`Receipt` types, the `data_map()`/`ropa()` signatures, the DSR
submit/status/certificate signatures, the audit-proof signatures. These are frozen in M0 so consumers compile
before the bodies exist. (b) A new runtime crate **myelin-gdpr-service** holds the GDPR/Audit service itself —
the DSR orchestrator, the data-map generator build step, the audit-log consumer + Merkle/STH machinery, the
retention/consent/sub-processor engine, the erasure ledger, the eDiscovery export. The service boots from an
`AppSpec` (it does not hand-roll a `main`). GDPR implements its contracts to the frozen shape; a needed shape
change is a whole-workspace contract PR, escalated and written down, not a local divergence (EI-01 §1,
code-wins-over-docs: if reality forces a divergence, write it in the crate doc comment and escalate).

**The single load-bearing fact this whole file sequences around:** GDPR/Audit owns no mechanism, so its
dependency on the things it orchestrates is a **fan-out-completeness** dependency (GA-D1 "0 holders missed" is a
property of the *generated data map*, and it can only be PROVEN complete once every holder H1–H18 exists — M5),
**not** a build-order blocker for its own spine (M1). Its four hard upstream blockers are all M0/M1: the M0
harness auto-registration hook (1.4), the M0 outbox (2.2, the audit log rides it), the M1 Identity pseudonym-map
lever (4.8), the M1 Storage KMS/crypto-shred/restore floor (11.3/11.4/11.5). The X-7 erasure posture is GDPR's
**one critical-path obligation**: it must be frozen in M1 (P-GA-07), before the Git data model freezes in M3
(pseudonymous-by-default commits).

**The `[OPEN — LEGAL]` discipline (EI-04 §4, VISION §3).** Several GDPR surfaces have a structural floor that
ships on the engineering clock and a residual that counsel/DPO ratifies in parallel. The rule binding every
such prompt: **the structural floor ships regardless of legal ratification; counsel ratification gates
publishing a posture as ratified, never building the floor.** A prompt that ships a floor names the floor and
its follow-on in writing; a `[TBD_LEGAL]` basis tag is a named residual, never a blocker. Date every status
note.
